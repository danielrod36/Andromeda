Grounding Context

Project: Cepheus Adventure — a Python TUI app implementing the Cepheus Engine SRD (System Reference Document) character creation pipeline as an interactive lifepath mini-game. Built on four architectural layers: an Engine (command funnel, state models, seeded dice, event audit log), Rulesets (protocol-based CE SRD constants and resolution logic), Themepacks (YAML-driven careers, skills, oracles, complications, missions), and a Textual TUI (interactive screens, character sheet, choice menu, narrative log with optional LLM narration).

Current chargen flow: roll_characteristics → choose_career → qualification → run_survival → run_advancement → choose_skills → run_aging → re_enlist → mustering_out → complete

Key model constraints: Character stores a single career string, flat skill dict (always +1), no credits/equipment/homeworld. CareerData has no commission or re-enlistment fields. TableRange forces 2D6 on all tables. The difficulty ladder and characteristic DM ladder have wrong values. Only 8 of 24 SRD careers exist, and 6 of those 8 have wrong check values.

External context: The canonical CE SRD chargen pipeline has 13 steps. All 24 careers are defined (17 ranked with commission/advancement, 7 non-hierarchy with 2 skill rolls/term). The SRD uses 1D6 for skill tables, a graduated 8-row aging table, an injury table with crisis mechanics, commission as a separate step from advancement, draft on failed qualification, career change with DM penalties, re-enlistment rolls with natural-12 forced stays, and mustering-out with rank-based bonus rolls. No comprehensive open-source CE chargen exists — every tool found (Blue Sun Consulting, justinaquinoGITB) is partial.

1. Fix Foundational Resolution Math

Risk and consequences Conf 98% Cx Low

Two functions in cepheus.py are wrong, and together they corrupt every die roll in the entire game. The difficulty ladder has Easy at +1 (SRD: +4), Difficult at −1 (SRD: −2), and Very Difficult at −2 (SRD: −4). The characteristic DM ladder returns −3 at score 0 (SRD: −2) and caps at +3 for all scores 15+ (SRD: +4 at 18–20, scaling to +6 at 24–26). Every qualification, survival, advancement, commission, aging, and future psionics check routes through these two functions. Fixing them is the prerequisite for trusting any check result.

Basis

direct: cepheus.py:58-65 — difficulty ladder: "easy": 1, "difficult": -1, "very_difficult": -2 (SRD: +4, −2, −4). cepheus.py:131-144 — if value <= 0: return -3 (should be −2), else: return 3 (caps at +3 for 15+, should reach +6). Docstring at cepheus.py:128-129 enshrines wrong values as authoritative.

Rationale

These are the most compound fixes by affected-call-site count. An "Easy" qualification check is currently 3 DM points harder than intended — turning trivial checks into risky ones. Low-stat characters (score 0–2) are penalized more harshly than the SRD intends (−3 vs −2), making survival checks deadlier for the most vulnerable characters. High-stat characters (18+) lose their reward (capped at +3 instead of +4+). The docstring's self-reinforcing wrongness means developers reading the code think the ladder is correct. Fixing these two functions corrects every past and future check simultaneously.

Downsides

Existing tests assert the old wrong values (e.g., aging tests that assume binary behavior) — they must be updated. Characters generated before the fix will have different skill sets and survival outcomes than post-fix characters, breaking any saved replays.

2. Universal Table Engine

Skill development Conf 95% Cx Medium

The TableRange model already has num_dice and die_size fields, and is_contiguous() already computes ranges dynamically from those fields — it works correctly for 1D6. But the defaults lock to num_dice=2, die_size=6, the docstring declares "All die tables use 2D6," and all 24 skill tables across 8 careers are forced into 2D6 ranges. This single phantom invariant (wrong defaults + wrong docstring, not wrong logic) blocks: 1D6 skill tables (audit B3), the 1D6 injury table (B13), correct benefit tables, future psionics tables, and the 4th Specialist Skills table (B14). Additionally, SkillTableRollCommand and BenefitRollCommand are near-duplicate roll→lookup→event pipelines that should be unified into a single generic TableRollCommand.

Basis

direct: base.py:66-76 — fields default to die_size: int = 6, num_dice: int = 2. base.py:78-95 — is_contiguous() computes expected_min = self.num_dice and expected_max = self.num_dice * self.die_size (already die-agnostic). base.py:113-114 — SkillTable docstring: "One of a career's three skill tables." Benefit tables already use num_dice: 1 successfully (careers.yaml:71-72), proving the fields work for 1D6.

Rationale

This is the highest-leverage single change in the codebase. Every table-based system — skill tables, injury tables, aging tables, benefit tables, psionics tables — flows through this one model. Today, adding a new table type requires cramming it into 2D6 ranges (silently wrong) or bypassing validation. After this fix, the entire table subsystem becomes data-driven: a contributor adds a new table as YAML only, with no Python changes. The generic TableRollCommand eliminates the ~30-line boilerplate pattern that each new Command class currently duplicates.

Downsides

All 24 existing skill tables need data correction (2D6→1D6 ranges). The lookup_table_result function currently silently clamps out-of-range rolls — this latent bug must be surfaced as an error rather than silently folded. Test assertions that assume 2D6 skill table behavior must be updated.

One model change unlocks every table system in the SRD.

3. Career Lifecycle Model

Career progression Conf 96% Cx High

Two model changes unlock 8 of the 20 audit findings. First, replace career: str on Character with career_history: list[CareerTerm] — each entry records career id, terms served, rank achieved, commission status, and exit reason. This makes multi-career lifepaths (draft, career change, re-enlistment) structurally possible. Second, complete CareerData by adding commission: CheckRef | None, re_enlistment: int, and has_hierarchy: bool, and making advancement optional. Commission becomes a separate roll (officer-track fork) from advancement (rank progression). Non-hierarchy careers (Scout, Drifter, etc.) get 2 skill rolls per term instead of wrong advancement checks.

Basis

direct: state.py:34 — career: str = "", set once at lifepath.py:182 (if success: state.character.career = self.career_id). base.py:140-157 — CareerData has qualification/survival/advancement (all required CheckRefs) but no commission, re_enlistment, or has_hierarchy. AdvancementCommand at lifepath.py:258-282 conflates commission with promotion. Scout and Drifter have advancement data they shouldn't (careers.yaml:362-364, 612-614).

Rationale

The single-string career field is the structural root cause blocking draft (B16), career change (B17), re-enlistment rolls (B12), commission separation (B8), the 2-skill-roll bonus for non-hierarchy careers (B9), and multi-career mustering-out. You cannot implement any of these by editing a phase — the model itself must change. The conflation of commission with advancement produces cascading errors: non-hierarchy careers roll advancement they shouldn't, they don't get the 2-roll bonus, and officer commissioning as a player choice doesn't exist. Once the model is correct, the engine changes are mechanical.

Downsides

High complexity — touches Character model, CareerData model, QualificationCommand, AdvancementCommand, compute_num_skill_rolls, TUI phase machine, narrator, character sheet widget, and LLM state view. Breaking change to save-file format. All existing tests that assume single-career must be updated.

4. Skill System Rebuild

Skill development Conf 94% Cx Medium

Three changes to the skill subsystem unlock basic training (B11), background skills (B10), cascade specialization, the Specialist Skills 4th table (B14), and the Advanced Education EDU 8+ prerequisite (B7). First, extend apply_skill_result to support level-0 assignment (for basic training) and cascade choice resolution (e.g., "Gun Combat" → "Slug Rifle"). Second, add a prerequisite predicate to SkillTable so Advanced Education can gate on EDU 8+ and basic training can gate on first-term-only. Third, add the Specialist Skills table type and allow 3–4 tables per career instead of the hardcoded three.

Basis

direct: lifepath.py:51-69 — apply_skill_result always does character.skills[result] = current + 1; no level-0 path, no cascade. base.py:113-117 — SkillTable has only name and entries; no prerequisite field. base.py:160-170 — SkillData has no parent/cascade field. TUI offers all tables freely (lifepath.py:412-426). The string "Specialist" does not appear anywhere in careers.yaml.

Rationale

Basic training is the most impactful skill mechanic after the tables themselves — it gives first-term characters all service skills at level 0 as baseline competence. Without it, a first-term Navy character starts with the same skills as a fifth-term one (minus rank bonus). The level-0 concept also underpins background skills: those skills start at 0, representing broad-but-shallow competence. The EDU 8+ gate creates a meaningful build decision: prioritize raising EDU to unlock Advanced Education, or take Service Skills now. The Specialist table holds the most career-defining skill content — it's what differentiates a Navy character from an Army character beyond flavor text.

Downsides

Cascade skills require TUI UX for specialization selection (a sub-choice when a cascade skill is rolled). The SkillData model gains a parent field — all 47 skills in skills.yaml need re-categorization. The Specialist table requires authoring new skill data for all careers.

5. Risk Engine with Teeth

Risk and consequences Conf 95% Cx Medium

Replace the binary aging check (2D6 vs static 8) with the SRD's 8-row graduated table: roll 2D6, subtract total terms as a negative DM, compare to a table where penalties scale from "reduce 1 physical by 1" (margin 0) to "reduce 3 physical by 2, reduce 1 mental by 1" (margin −6 or worse). Then wire the injury table into survival mishap resolution: survival failure rolls 1D6 on the injury table with specific characteristic reductions, and if any characteristic hits 0, an injury crisis occurs (pay Cr10,000 or die). Mishap becomes a cascading consequence chain, not a career-exit flag. The existing Injury model gets real mechanics instead of being display-only.

Basis

direct: lifepath.py:26 — _AGING_TARGET = 8. lifepath.py:344-361 — binary check with no terms-as-negative-DM; only distinction is natural-2 reduces all 6 vs 3 physical. lifepath.py:233 — mishap just sets mishap = True and breaks the term loop. state.py:73-83 — Injury model has severity: str (display-only, no stat reduction). Audit B4: "Neither the mechanic nor the table matches the SRD." Audit B13: "No injury table, no injury crisis."

Rationale

Aging is the risk/reward governor that makes chargen a "game within a game" rather than a deterministic generator. The binary implementation eliminates all tension: roll 7 and nothing happens, roll 6 and you lose 3 stats — a cliff edge with no graduated middle ground. The SRD's graduated table creates a smooth ramp where a 2-term character (age 26, margin −2) loses 1 stat while a 6-term character (age 38, margin −6) loses 5 stats — fundamentally different consequences. The injury table makes survival failure meaningful without being instantly fatal: the character who survives a crash, loses 1D6 DEX, and faces a crisis with no credits is in a dramatically different position than one who simply musters out.

Downsides

The TUI button label hard-codes the wrong target ("Roll Aging (2D6 vs 8)") and must be updated. Tests that assert binary aging behavior must be rewritten. The injury crisis mechanic requires a credits field on Character (depends on idea 7) to make the "pay Cr10K" decision meaningful.

6. Pre-Career Foundation

Pre-career setup Conf 85% Cx Medium

Add the missing phase between characteristics and career choice: background skills and basic training. Background skills grant 3 + Education DM skill picks — the first 2 from a lightweight origin archetype (Spacer, Colonist, Belter, Frontier, Urban) that pre-resolves homeworld trade-code skills without requiring a full world-generation subsystem, and the remainder from the education skill list. Basic training grants all service skills at level 0 on first career entry (first career: all; subsequent careers: one). This makes characteristics consequential beyond roll modifiers: EDU determines the skill budget, INT gates education tracks, and the archetype provides origin identity.

Basis

direct: TUI phase machine at lifepath.py:199-204 jumps directly from roll_characteristics to choose_career — no background phase exists. characteristic_dm() at cepheus.py:125-144 is only called for qualification/survival/advancement, never for skill allocation. apply_skill_result at lifepath.py:51-69 has no level-0 path. Audit B10: "SRD: Before careers, gain skills = 3 + Education DM. Our code: Not implemented." Audit B11: "First term = ALL Service Skills at Level 0. Not implemented."

Rationale

Without background skills and basic training, every character enters career choice at age 18 with zero skills — a blank slate who somehow joined the Navy without knowing anything. Background skills give characters their pre-career identity (homeworld origin, education). Basic training gives them baseline competence (all service skills at level 0). The archetype lookup avoids the disproportionate scope of building a full world-generation engine (UWP codes, starports, trade codes) to extract 2 skill slots — the project's own research docs flag world-gen as "high-code, low-narrative-yield under an LLM." This also makes the initial 2D6 characteristic rolls the most strategically important moment in chargen, since EDU directly determines skill count.

Downsides

Requires a new themepack YAML structure for origin archetypes and education skill lists. The TUI phase machine gains 2 new phases (background_skills, basic_training). Depends on idea 4 (apply_skill_result level-0 support) and idea 1 (correct EDU DM for skill budget calculation). The archetype approach is a simplification of the SRD's trade-code system — purists may want full world generation instead.

7. Benefits Persistence + Career Data Integrity

Post-chargen and beyond Conf 92% Cx Medium

Two critical post-chargen fixes. First, parse mustering-out benefit strings into persistent Character state: cash amounts ("5,000 Cr") become a numeric credits: int field, material benefits ("Weapon", "Ship Share") become typed inventory entries. Currently the entire mustering-out phase produces zero persistent state — BenefitRollCommand.mutate generates Events but never modifies state.character, and the MusteringOutResult is discarded after narration. Second, systematically regenerate career data for all 24 SRD careers with a validation harness that checks qualification/survival/commission/advancement/re-enlistment targets against SRD references — 6 of the 8 existing careers have wrong check values, 2 have advancement they shouldn't, and 16 careers are entirely missing.

Basis

direct: lifepath.py:379-411 — BenefitRollCommand.mutate produces an Event with result_text but does NOT modify state.character. state.py:29-36 — Character has no credits or equipment field. lifepath.py:803-835 — _finish_mustering_out only sets SetFlagCommand(key="mustered_out", value="true"). Agent career at careers.yaml:435-443: qualification INT 5 (SRD: SOC 6), survival INT 5 (SRD: INT 6), advancement INT 7 (SRD: EDU 6). Only 8 of 24 careers exist (audit B20).

Rationale

From the player's perspective, mustering out feels broken: you watch benefits get announced, then the character sheet shows nothing. The character enters the adventure loop structurally identical to one who mustered out with nothing. This is the bridge between chargen and play — without it, the career-progression arc is a narrative exercise with no mechanical payoff. The career data integrity issue is equally critical: a character who qualifies for Agent rolls against the wrong characteristic, survives at the wrong target, and advances through the wrong stat. Hand-fixing 8 careers is manageable; hand-authoring 24 correctly without a validation harness is not — the audit already documents transcription errors in the existing data.

Downsides

Benefits persistence requires deciding on the equipment/gear model (typed entities vs. string list). The 24-career regeneration is a significant data-entry effort requiring careful SRD verification. The dm_per_rank and benefit table structures need to be re-verified for correctness (only 3 of 8 careers currently set dm_per_rank).
